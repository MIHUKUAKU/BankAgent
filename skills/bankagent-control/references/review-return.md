# 审核、直接退修与完成通知

## 送审
执行员完成本企7—9月整包后，直接向本企固定审核员提交正式审核任务，不等待其他企业或总控放行。其他任务按本岗范围提交。任务含task_id、责任人、输入/产物路径及哈希、scope、验收条件和历史修复记录。审核员无候选时记录待输入，不假装已审核。

## 未通过
审核员保存绑定确切哈希的REVISE/REJECT结论，一次列全问题，立即直接退原执行员修订。执行员追加版本和逐项回应，直接回原审核员；不经总控中转。原拒绝结论保留，修订必须解决问题，不能绕过理由或更换身份自审。
“无需重复搜索”只约束取数，不免除正式退修、估计、修订、送审或完成通知。已知问题无需重新搜索即可依据现有证据退修；缺口清单、审核文件和对总控的说明均不代替向执行员实际派发修订任务。

审核失败后的本轮交付包括两部分：保存审核结论，以及调用通信工具向原执行员正式退修。退修消息须带task_id、企业/月度、确切版本或manifest哈希、审核文件路径、一次列全的阻塞项、可执行修复要求和回送原审核员的要求。没有新增证据时直接复用原证据；缺内部参数时允许有依据估计或替代计算，不能只要求补齐资料再继续。

审核员结束本轮前核对并保存退修路由记录（与审核文件并列或写入该轮工作记录）：task_id、审核文件及哈希、接收执行员聊天ID、发送时间、发送结果，以及工具返回的消息/请求ID（若有）。状态区分`return_pending`（待发送）、`return_dispatch_failed`（发送失败）、`return_dispatched`（接口已接受）、`revision_in_progress`（已观察到执行员开始修订）。接口接受不等于对方已收到或开始工作；没有工具成功结果不能写“已退修”。

REVISE/REJECT仍为`return_pending`时，本轮审核流程未完成，须继续发送，不能以“已记录缺口”“无需再搜”“等待执行”结束。接口失败则保存实际错误，核对目标后进行有依据的重试；仍不可达时保留待退修状态并报告通信阻塞，不冒称发送成功。恢复任务时先读最近审核及路由记录，补发遗漏的退修；对同一哈希、同一问题且已有成功发送记录的任务不重复派发，无新增证据不重审。
历史轮次照实记录，不以轮次耗尽自动停工。每轮须有实质修复，不无变化循环；缺证据转有依据估计或替代方法，权限故障记录实际阻塞并继续可完成部分，不越权。未变PASS不重审。

## 通过与上报
产品推荐交付须包含可复算的量化推荐顺位。只通过公式、阈值或比较器的审核记为部分成果，不能报任务已完成；审核员应明确缺项并直接退原作者继续补足。缺失数据时仍须给出推荐顺位，由声明的基准情景、估计和可复算比较推导，并写明取舍及换位条件。审核允许合理估计和显式情景下的推荐，不能只因缺实测项目参数要求删除全部排名；不得用定性询价名单或空集合替代。
固定审核员彻底通过后保存审核文件和完成回执，主动向总控简报“已完成”，附task_id、企业/月度、产物清单、审核及回执路径。无需复述全报告或请求总控逐条批准。总控自行读取、核对哈希与状态后记账。
完成通知是必要工作通信，不能省略；候选写完不等于审核完成，不能拿旧PASS上报新版本。失败只直退作者，完成回执不能代替发布记录。企业发布与月度账本见[发布规则](reviewer-publication-ledger.md)。

市场免例行审核；有证据争议直接交金融审核员。方法研究由用户直阅。无新增停止的是对应网络搜索，不是项目；转估计或替代方法继续计算、修订与交付。
